
## Раздел 1. Постановка

| поле                        | решение                                                                                                                                                                             |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Бизнес-действие             | Планировщик корректирует численность и смены по прогнозу потока и диапазону неопределённости, сохраняя за собой утверждение расписания                                              |
| Объект и единица решения    | Число входящих обращений и workload одной очереди/канала за временной интервал                                                                                                      |
| Момент                      | Пакетно: недели вперёд для графика; обновление на день/час для оперативного управления                                                                                              |
| Операция                    | Вероятностный числовой прогноз временного ряда; расписание строит отдельный оптимизатор                                                                                             |
| Модальность                 | Временные ряды и таблицы: факты обращений, AHT, календарь, кампании, релизы и известные будущие события                                                                             |
| Выход модели                | Медиана и согласованные квантили числа обращений/workload, интервал прогноза, флаг out-of-distribution                                                                              |
| Бизнес-выход                | Требуемая численность, сценарии SLA/стоимости и предупреждение дефицита; утверждённое человеком расписание                                                                          |
| Источник правильного ответа | Фактически поступившие обращения и workload после закрытия интервала; бизнес-эффект - SLA, abandon rate, occupancy, overtime и оплаченные часы                                      |
| Конвейер                    | Валидация событий -> агрегация -> known-in-advance признаки -> прогноз -> Erlang/дискретная оптимизация -> интерфейс планировщика -> факт и мониторинг                                    |
| Альтернативные постановки   | Прогноз calls, прогноз workload или готовое расписание. Для пилота - calls и workload по очереди; оптимизатор оценивается отдельно, чтобы не смешивать ошибки прогноза и расписания |

## Раздел 2. Оценка качества

| поле                       | решение                                                                                                                                                                                                                       |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Бизнес-метрика             | SLA, abandon rate, overtime, occupancy, оплаченные часы и стоимость относительно действующего плана                                                                                                                           |
| Положительный класс        | Не применимо: целевая величина числовая. Отдельно контролируются интервалы пикового спроса и дефицита мощности                                                                                                                |
| Метрика под решение        | WAPE для агрегированной ошибки, MASE для сравнения очередей, pinball loss и coverage квантилей. Главный выбор - симуляция стоимости staffing и SLA на исторических периодах. MAPE не используется на малых/нулевых очередях   |
| Baseline                   | Действующий ручной/системный прогноз, seasonal naive по тому же часу недели, затем ETS/SARIMAX                                                                                                                                |
| Проверочная выборка        | Rolling-origin backtest без случайного перемешивания. Отдельные срезы: обычные недели, праздники, конец месяца, кампании, массовые сбои, изменения маршрутизации и новые очереди                                              |
| Рабочая точка              | Квантиль выбирается из отношения стоимости недопланирования к перепланированию: `q = C_under / (C_under + C_over)`, затем workload переводится в штат при целевом SLA                                                         |
| Показатели в рабочей точке | Кандидат должен превзойти seasonal baseline и действующий план по backtest и симулированной стоимости; интервал должен быть калиброван. Расписание не выкатывается автоматически до shadow-периода                            |
| Цена ошибок                | Недопрогноз - потерянные обращения, ухудшение SLA и перегрузка; перепрогноз - простой и лишние часы. Цена различается по очередям и времени                                                                                   |
| Guardrails                 | Не ухудшаются SLA и нагрузка сотрудников; ограничения труда и навыков соблюдаются оптимизатором; ручной override и fallback доступны; непредсказуемые инциденты обрабатываются сценарием, а не маскируются точечным прогнозом |

### Приёмочный набор и пороги

1. Нужна история, содержащая не менее 6 повторений самой длинной проверяемой
   сезонности; для годовой сезонности предпочтительны 2 года. При меньшей
   истории годовые эффекты задаются календарными правилами и явно считаются
   неопределёнными
2. Backtest включает минимум 8–12 последовательных forecast origins для
   каждого рабочего горизонта и все доступные редкие события. Последние
   8–12 недель не используются в обучении при финальной оценке
3. Метрики считаются по очередям и взвешиваются бизнес-стоимостью, а не только
   объёмом. Новые и низкообъёмные очереди выделяются отдельно
4. Минимальный технический gate: `MASE < 1` против seasonal naive, нижняя
   граница 95% bootstrap-интервала улучшения WAPE выше нуля, coverage 80%
   интервала находится в диапазоне 75–85%. Последний допуск +-5 п.п. -
   предварительное операционное требование к калибровке, утверждаемое
   владельцем WFM
5. Бизнес-gate: историческая симуляция при одинаковом SLA показывает
   положительную экономию сверх TCO либо при одинаковой стоимости улучшает
   SLA. Минимальная экономически значимая разница фиксируется владельцем
   процесса до просмотра результатов

Провал только на кампаниях означает отсутствие/ошибку known-future признаков и
требует обязательного календаря кампаний. Провал на сбоях не лечится
`угадыванием` неизвестного инцидента: нужен оперативный override. Провал на
новых очередях требует pooled/global модели или fallback. Если forecast хорош,
а SLA нет - проблема вероятнее в AHT, shrinkage или оптимизаторе

### Размещение и шортлист

**Жёсткие ограничения:** в модель не поступают аудио, текст разговора и
идентификаторы клиента; обучение и inference воспроизводимы; известность
признака фиксируется на момент прогноза; есть fallback и ручной override

**Пилот:** изолированная аналитическая среда on-prem на агрегатах.
**Прод:** self-hosting в одобренном частном облаке или on-prem. Публичный API
не нужен: задача компактна, а зависимость и передача данных не дают
компенсирующей ценности

Шортлист:
1. seasonal naive - обязательный baseline
2. ETS/SARIMAX с календарными регрессорами - интерпретируемый кандидат;
3. global LightGBM/CatBoost с lag/rolling и known-future признаками,
   quantile loss - кандидат для многих очередей
4. глубокая temporal-модель - допускается только при большом числе стабильных
   рядов и доказуемом выигрыше после учёта GPU/TCO

Все кандидаты возвращают одинаковые квантили и проходят один rolling backtest.
Побеждает не минимальная средняя ошибка, а минимальная бизнес-стоимость при
калиброванных интервалах. Если ML не превосходит seasonal/statistical
baseline, выбирается более простая модель. Если ни один прогноз не улучшает
staffing, проект останавливается либо исправляются данные/оптимизатор

## Раздел 4. Карточка эксперимента

| поле                            | решение                                                                                                                                                                        |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Где именно теряем ?             | Предположительно пики, праздники и кампании приводят к дефициту, а спокойные интервалы - к избыточным сменам; факт подтверждается data audit                                   |
| Гипотеза причины                | Текущий план недостаточно учитывает множественную сезонность, кампании и асимметричную цену недопрогноза                                                                       |
| Конкурирующие объяснения        | Прогноз уже достаточен, а потери создают неточный AHT, shrinkage, skill routing, ограничения расписания или незарегистрированные инциденты                                     |
| Рычаг                           | Известные события, pooled forecast, quantile loss, выбор рабочей точки и отдельный staffing simulator                                                                          |
| Дешёвый различающий эксперимент | Rolling backtest четырёх кандидатов плюс историческая симуляция staffing; затем 4–8 недель shadow forecast без изменения смен                                                  |
| Ожидаемый эффект                | Не задаётся произвольно: владелец WFM фиксирует MDE в рублях/SLA по TCO. Требуются статистически положительный uplift к seasonal baseline и положительный бизнес-эффект        |
| Стоимость проверки              | 1–2 недели data audit, витрина агрегатов, backtest и участие WFM в функции стоимости; GPU на пилоте не требуется                                                               |
| Критерий остановки              | Нет непрерывной истории; MASE >= 1; интервалы некалиброваны; staffing simulation не даёт выгоды; улучшение исчезает в shadow; процесс не регистрирует будущие кампании вовремя |
