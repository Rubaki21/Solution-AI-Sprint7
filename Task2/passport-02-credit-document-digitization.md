
## Раздел 1. Постановка

| поле                        | решение                                                                                                                                                                                              |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Бизнес-действие             | Предзаполнить карточку кредитной заявки из документов, чтобы андеррайтер проверял и исправлял результат вместо полного ручного ввода                                                                 |
| Объект и единица решения    | Документ/страница и отдельное поле; бизнес-единица - пакет одной заявки                                                                                                                              |
| Момент                      | Асинхронно после загрузки и до начала анализа заявки                                                                                                                                                 |
| Операция                    | Классификация типа, OCR, извлечение структуры и полей                                                                                                                                                |
| Модальность                 | PDF, изображение/фото, текст, таблица, Excel                                                                                                                                                         |
| Выход модели                | Версионированный JSON: тип документа, `field_id`, значение, нормализованное значение, страница/координаты, confidence, флаг нечитаемости и версия модели                                             |
| Бизнес-выход                | Предзаполненная форма с привязкой к оригиналу и очередью обязательной проверки; неподдерживаемый/нечитаемый документ уходит в ручной ввод                                                            |
| Источник правильного ответа | Подтверждённые сотрудником значения и исправления, сверенные с оригиналом; gold-набор размечается независимо двумя специалистами для критичных полей                                                 |
| Конвейер                    | Malware/format check -> нормализация -> классификация -> OCR/layout extraction -> правила формата и арифметики -> confidence routing -> подтверждение сотрудником -> запись результата и исправлений |
| Альтернативные постановки   | Только поисковый OCR, извлечение полей или расчёт показателей. Пилот ограничен извлечением согласованного набора полей из 2–3 наиболее частых типов документов                                       |

## Раздел 2. Оценка качества

| поле                       | решение                                                                                                                                                                                                                                                                                  |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Бизнес-метрика             | Медианное и p90 активное время андеррайтера на пакет, доля полей без исправления, доля пакетов, возвращённых в полный ручной ввод, и ошибки после подтверждения                                                                                                                          |
| Положительный класс        | Для классификации - конкретный тип документа. Для извлечения нет единого положительного класса: качество считается по каждому критичному полю и сценарию; отдельное событие - ошибочно принятое значение                                                                                 |
| Метрика под решение        | Exact match после согласованной нормализации для идентификаторов/сумм/дат; tolerance accuracy только для полей с утверждённым допуском; precision/coverage кривые confidence routing; macro-F1 по типам; CER/WER - только диагностические                                                |
| Baseline                   | Полный ручной ввод и время 1,5 часа на пакет. Технический baseline - OCR без layout-модели плюс шаблонные правила                                                                                                                                                                        |
| Проверочная выборка        | Клиенты, пакеты и шаблоны не пересекаются с обучением; временной holdout. Страты: native PDF, чистый скан, фото, поворот/блики/низкое разрешение, таблицы, разные бухгалтерские системы, типы и версии форм                                                                              |
| Рабочая точка              | На пилоте 100% критичных полей подтверждает человек; confidence задаёт только порядок проверки. Автопринятие может рассматриваться позже по отдельному ADR и полевой precision/coverage                                                                                                  |
| Показатели в рабочей точке | Принимается кандидат, который при обязательной проверке уменьшает медианное активное время не менее чем на заранее согласованный бизнесом MDE и не увеличивает ошибки после подтверждения. Конкретный MDE фиксируется до эксперимента на основе стоимости интеграции и часа андеррайтера |
| Цена ошибок                | Ложное значение критичного поля способно исказить кредитный анализ; низкая coverage сохраняет ручной труд; неверный тип документа направляет поля в ошибочную схему                                                                                                                      |
| Guardrails                 | Нет автоматического кредитного решения; исходник всегда доступен; критичные поля подтверждаются; неизвестная форма не маскируется под известную; документы и логи не выходят из одобренного контура                                                                                      |

### Приёмочный набор и пороги

- После инвентаризации взять не менее 200 документов каждого пилотного типа:
  при ожидаемой доле правильного поля около 95% это даёт приблизительно
  ±3 процентных пункта 95% интервала для частого бинарного показателя.
  Окончательный размер пересчитывается по фактической частоте полей и
  кластеризации ошибок внутри документа
- Для каждого критичного поля требуется не менее 200 независимых появлений и
  покрытие всех известных форм. Если валидация будущего автопринятия требует
  показать ошибку ниже 0,5%, нужно около 600 независимых наблюдений без ошибки
  (rule of three, верхняя 95% граница); до этого автопринятие запрещено
- Включить не менее 100 телефонных фото и все доступные редкие/повреждённые
  сценарии; малые группы описывать интервалами, не скрывать общей средней
- Минимальные pilot gates: macro-F1 типа документа ≥0,95; exact match каждого
  критичного поля >= 0,95 при 100% human review; неизвестные типы должны
  маршрутизироваться вручную. Это не «качество рынка», а предварительные
  требования процесса, которые владелец андеррайтинга и риск должны утвердить
  до теста
- Главный бизнес-gate: нижняя граница 95% интервала сокращения активного
  времени выше согласованного MDE, а ошибки после проверки не хуже ручного
  baseline по non-inferiority margin владельца риска

Провал на фото означает необходимость image-quality gate/повторного запроса, а
не замену всей модели. Провал на одном шаблоне требует отдельного extractor или
ручной маршрут. Высокий OCR при низком exact match таблиц означает, что
проблема в layout/table extraction. Галлюцинация отсутствующего значения -
жёсткий дефект кандидата

## Раздел 3. Готовность данных

| поле                          | решение                                                                                                                                                                                                                                      |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Решение                       | Предзаполнение полей с обязательной проверкой, не автономный андеррайтинг                                                                                                                                                                    |
| Объект и гранулярность        | Пакет -> документ -> страница -> поле и его координаты                                                                                                                                                                                       |
| Источник и владелец           | DMS/кредитный конвейер - кредитные операции; карточка заявки и ручные значения - андеррайтинг; справочник схем - методология риска; платформа хранения/доступа - ИТ и data platform                                                          |
| Источник правильного ответа   | Gold-разметка по оригиналу и журнал подтверждений/исправлений. Итоговое кредитное решение не является эталоном корректности извлечения                                                                                                       |
| Доступность признаков в проде | Оригинал доступен при загрузке. Внешние справочники и валидации должны иметь версию на момент обработки                                                                                                                                      |
| Разметка                      | Схема полей и guideline на тип документа; двойная разметка критичных полей; исправления UI пишутся как old/new value, источник, пользователь, причина и версия extractor                                                                     |
| Смещение отбора               | Архив может содержать преимущественно одобренные или завершённые заявки; сотрудники могли вручную отбрасывать нечитаемые файлы. Выборка строится от момента загрузки всех документов, включая отклонённые и заменённые                       |
| Репрезентативность            | Типы организаций, формы, бухгалтерские системы, банки, native PDF/скан/фото, устройства, качество, языки и изменения шаблонов во времени                                                                                                     |
| Объём                         | В условии не указан. До выбора модели нужны частоты по типам, страницам, полям и доля низкокачественных изображений. Важный «класс» - каждое критичное поле и каждый пилотный тип, а не число файлов вообще                                  |
| Качество                      | Проверить связь документа с заявкой, дубли/версии, повреждения, DPI/поворот, пароль, пустые страницы, единицы/валюты, согласованность ручной карточки с оригиналом и журнал исправлений                                                      |
| Право использовать            | Документы могут содержать банковскую тайну и персональные данные заёмщиков, представителей и поручителей. Юристы/DPO/комплаенс/ИБ решают цель, основание, регион, хранение, доступ, допустимость предобученной модели и внешнего обработчика |
| Вердикт                       | **Разрыв с планом закрытия.** Не подтверждены каталог, объёмы по формам/полям и пригодность ручных исправлений как эталона. Закрытие: 2-недельная инвентаризация -> схема пилота -> gold-set -> журнал исправлений -> теневой тест           |

### Размещение и шортлист

**Жёсткие ограничения:** сырые документы не передаются публичному API без
положительных заключений и договора; результат воспроизводим и аудируем;
оригинал и координаты сохраняются; неизвестные/низкоуверенные случаи имеют
ручной fallback; обучение провайдера на документах банка запрещено без
отдельного основания

**Пилот:** on-prem в изолированном контуре. **Прод:** on-prem либо выделенный
контур/self-hosting в одобренном облаке после проверки региона, обработчиков,
изоляции, удаления и exit plan. Публичный API на текущем этапе отсечён

Кандидаты под JSON-контракт:
1. self-hosted OCR (PaddleOCR/Tesseract-класс) + детерминированные шаблоны -
   baseline для стабильных форм
2. self-hosted layout-aware encoder (LayoutLMv3-класс) для полей и таблиц
3. self-hosted OCR-free document model (Donut-класс) только при строгой
   проверке пропусков/галлюцинаций и возможности привязки к источнику
4. выделенный document-AI провайдер - только после прохождения правового и ИБ
   gate; сравнивается тем же закрытым набором

Итог определяется полевым exact match, confidence/coverage, временем и TCO на
приёмочном наборе, а не публичным рейтингом. Если сложная модель не даёт
значимого выигрыша над OCR+rules, выбирается baseline. Если ни один кандидат
не проходит критичные поля, охват сужается либо сохраняется ручной ввод

## Раздел 4. Карточка эксперимента

| поле                            | решение                                                                                                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Где именно теряем ?             | Неизвестно, какая доля 1,5 часа уходит на чтение, ввод, сверку и расчёт; ожидаемая просадка - фото, таблицы и вариативные формы                                    |
| Гипотеза причины                | Предзаполнение частых полей из 2–3 типов документов уменьшит повторный ручной ввод без роста подтверждённых ошибок                                                 |
| Конкурирующие объяснения        | Основное время уходит не на ввод, а на смысловой анализ; ручные значения ненадёжны как эталон; формы слишком разнообразны; UI проверки съедает выигрыш             |
| Рычаг                           | Ограничение типов, quality gate, модель layout extraction, правила валидации, confidence routing и интерфейс подтверждения                                         |
| Дешёвый различающий эксперимент | Time-and-motion замер 30–50 пакетов; затем offline benchmark кандидатов на gold-set и shadow/UI-тест на тех же типах без влияния на решение                        |
| Ожидаемый эффект                | MDE определяется из TCO и стоимости часа до раскрытия теста; статистически подтверждается сокращение активного времени при non-inferior качестве                   |
| Стоимость проверки              | Инвентаризация, 600+ документов для трёх типов как стартовый набор, двойная разметка критичных полей, on-prem inference и прототип UI                              |
| Критерий остановки              | Ввод составляет малую долю времени; нет правового допуска; критичные поля не проходят gate; UI не сокращает время; объёма частых форм недостаточно для окупаемости |
