
Статус: **предварительное**

Дата: 2026-10-10

Инициатива: распознавать и оцифровывать сканы документов кредитной заявки

## Контекст

`underwriting` тратит в среднем 1,5 часа на пакет. Документы разнородны и могут
содержать банковскую тайну и персональные данные. Модель должна извлекать
поля, но не принимать кредитное решение

## Жёсткие ограничения

- Непроверенные критичные поля не поступают в decisioning
- Оригинал, страница/координаты, версия модели и исправления аудируются
- Недоверенный файл проходит quarantine до parser/model
- Публичный API не используется без заключений юристов, DPO, комплаенса и ИБ
- Модель не имеет сетевых инструментов, секретов и права записи в кредитный
  конвейер

## Рассмотренные варианты

| вариант                    | за                                  | против                                       | решение                   |
| -------------------------- | ----------------------------------- | -------------------------------------------- | ------------------------- |
| Публичный Document API     | Быстрый старт                       | Передача чувствительных документов и lock-in | Отсечён на пилоте         |
| On-prem OCR + шаблоны      | Дёшево, объяснимо                   | Слабо на вариативных формах                  | Baseline                  |
| On-prem layout-aware model | Лучше поля/таблицы, остаётся внутри | Нужны gold-set и MLOps                       | Основной кандидат         |
| OCR-free document model    | Единый extraction                   | Риск галлюцинаций/нет source grounding       | Challenger с жёстким gate |
| Выделенный контур          | Managed и возможное качество        | Договор/регион/exit и внешний обработчик     | Резерв после согласования |

## Решение

Пилот on-prem на 2–3 частых типах: карантин -> preprocessing -> OCR/layout
extraction -> schema/format/arithmetic validation -> обязательное подтверждение
критичных полей -> запись. Сравнить OCR+rules, layout-aware и OCR-free
кандидата по закрытому gold-set. Прод остаётся on-prem либо переходит в
одобренный выделенный/private контур только после отдельного gate

Данные: инвентаризация всех загрузок, включая отклонённые/заменённые; не менее
200 документов каждого пилотного типа и 200 появлений каждого критичного поля;
исправления сохраняются как old/new/reason. Побеждает кандидат по field exact
match, false-high-confidence, времени проверки и TCO, а не по общему OCR

## Допущения

- Частые формы дают достаточный объём и долю ручного времени
- DMS может хранить hash, версии и координаты без нарушения сроков хранения
- Андеррайтеры выделят время на gold-set и подтверждение

## Риски и меры

Недоверенный контент изолируется; галлюцинации блокируются source grounding и
status gate; drift форм контролируется; ручной ввод остаётся fallback

## План выхода

JSON-контракт, schema registry, gold-set и correction log принадлежат банку;
модель заменяема за adapter; ручной ввод обслуживает 100% документов. Внешний
договор должен обеспечить экспорт, удаление, уведомление об изменениях и
миграцию

## Триггеры пересмотра

- извлечение не сокращает активное время
- критичное поле не проходит exact-match/false-confidence gate
- меняется уровень автоматизации или допускается автопринятие
- контрольные функции запрещают источник/размещение
- выделенный контур доказывает лучшее качество/TCO при выполнении ограничений
